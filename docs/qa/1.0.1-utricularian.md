# MVP release-candidate scenario checklist

Use this document to verify the combined RGMS MVP in a live World of Warcraft
Retail client. It is deliberately self-contained: a tester should not need an
issue, design note, or another checklist to know the setup, action, or expected
result.

Do not mark an item complete from memory. Record the observed result, and attach
the completed copy to the release-candidate evidence. The automated companion
scenarios use the fixed Pacific dates listed below and run with:

```text
lua Tests/run.lua
```

Expected result: the command exits with status `0` and reports zero failed
tests. Failures whose names begin with `MVP-E2E-` also identify the named
transition that failed.

`YYYY-MM-DD HH:MM PT`.

## Scenario 1 — guilded first login, persistence, and reload

Precondition: Character A is in Guild A and has no `RGMSCharacterDB`.

- [ ] Log in on Character A.
  - Chat: `RGMS: [development] loaded. Type /rgms help for available commands.`
    followed by `RGMS: Guild roster scan complete: <member count> members across
    <rank count> ranks.`
  - UI: opening `/rgms` shows Roster. During collection it says `Updating...`;
    afterward it shows all configured ranks and `Last successful update:
    <YYYY-MM-DD HH:MM PT>`.
  - Timestamp: `roster.scannedAt` is the successful scan time; every current
    member's `observedAt` matches it. New tenure and last-seen dates equal the
    scan's Pacific date.
  - Persisted state: `roster.guild` is Guild A and the complete rank/member
    snapshot is present. Bank remains empty and UI position is unchanged.
- [ ] Run `/reload`.
  - Chat: the loaded message appears; a new automatic success may follow.
  - UI: no empty or corrupt-data flash; the last committed report remains
    usable and is replaced only after a complete new scan.
  - Timestamp: before a new success, the prior `scannedAt` remains visible. A
    new success advances it.
  - Persisted state: the pre-reload complete dataset survives; no partial model
    appears.

## Scenario 2 — unguilded login, then manual scan after joining

Precondition: Character B is unguilded and has no `RGMSCharacterDB`.

- [ ] Log in on Character B, open `/rgms`, and select Roster.
  - Chat: only the loaded message; the automatic unguilded request is silent.

  - Persisted state: roster ranks/members remain empty.

  - Timestamp: a new Pacific-rendered successful time appears.

## Scenario 3 — same-day, multi-day, rank, missing, and reappearance rules

The exact 22-day boundary is required automated evidence (`MVP-E2E-03`). The
live checks below validate the Retail event/API path without requiring a
22-calendar-day release test.

- [ ] Complete two successful roster scans on the same Pacific date without
  changing the test member's numeric rank.
  - Chat: one success line per completed scan.
  - UI: the member remains in the same numeric rank tab.
  - Timestamp: `scannedAt` and `observedAt` advance; `rankTenureStartDate` does
    not change.
  - Persisted state: only the latest complete observation is retained.
- [ ] Rename that rank and scan again.
  - Chat/UI: success; the new rank label appears.
  - Timestamp/state: numeric rank is unchanged, so tenure start is preserved.
- [ ] Promote, scan, demote, and scan the test member.
  - Chat/UI: each success moves the member to the expected rank tab.
  - Timestamp/state: each numeric rank-index change resets tenure to that
    scan's Pacific date.
- [ ] Remove the member from Guild A and scan successfully.
  - Chat: normal success, not a failure.
  - UI: the member remains visible with the missing warning and a tooltip whose
    last-appeared date is the prior `lastSeenDate`.
  - Timestamp/state: dataset `scannedAt` advances; the retained member keeps
    its prior `observedAt`, `lastSeenDate`, and tenure start; `isMissing=true`.
- [ ] Reinvite the member and scan successfully.
  - UI: the missing warning disappears.
  - Timestamp/state: `isMissing=false`, `observedAt` and `lastSeenDate` advance,
    and tenure restarts even if the member returns at the same numeric rank.
- [ ] Confirm automated `MVP-E2E-03` retained the absent member on 2024-06-24
  (21 missing days) and removed it on 2024-06-25 (22 missing days).

## Scenario 4 — roster timeout/failure with prior data and window closed

Retail does not expose a safe deterministic switch for withholding guild
events. The failure/timeout transitions are required automated evidence in
`MVP-E2E-04`; the live portion verifies that closing RGMS does not cancel the
Retail-driven roster transaction.

- [ ] With prior roster data, click Refresh and immediately close RGMS. Wait for
  the normal completion event, then reopen `/rgms`.
  - Chat: normal roster success. If Retail itself fails, the message begins
    `RGMS: Guild roster scan failed:` and describes the reason.
  - UI: closing RGMS hides the window but does not cancel the scan; reopening
    shows the last complete report.
  - Timestamp/state: success advances the complete dataset. An actual failure
    or 15-second timeout must leave the prior timestamp and dataset byte-for-
    byte equivalent in meaning.
- [ ] Confirm automated `MVP-E2E-04` produced
  `Guild roster scan failed: timed out before complete guild-roster data
  arrived.` and preserved prior state for both timeout and API failure.

## Scenario 5 — guild bank mixed access, success, and persistence

- [ ] Open the default Guild Bank on Character A.
  - Chat: `RGMS: Guild bank scan complete: <purchased> purchased tabs,
    <accessible> accessible, <occupied> occupied slots.`
  - UI: RGMS opens on Bank and aligns beside the bank unless a manual RGMS
    position was saved. Refresh is disabled during `Scanning...` and enabled
    after success while the bank remains open.
  - Timestamp: `bank.scannedAt` is the completion time. Accessible tabs receive
    that `lastAccessibleAt`; every captured occupied slot receives it as
    `observedAt`.
  - Persisted state: every purchased tab is recorded. Accessible tabs show
    contents; inaccessible tabs show `No access` and are never queried for
    contents.
- [ ] Close the bank, `/reload`, reopen `/rgms`, and select Bank without opening
  the bank again.
  - Chat: no bank scan starts merely from opening RGMS.
  - UI: `Guild bank closed. Last successful scan: <...>`; prior report remains
    visible and Bank refresh is disabled.
  - Timestamp/state: the successful bank dataset survives reload unchanged.

## Scenario 6 — bank item stability transitions

After each change, reopen or refresh the guild bank and wait for the success
message. Record the value shown in the Bank report and in SavedVariables.

| Action | Expected UI and timestamp | Expected persisted change |
| --- | --- | --- |
| Leave item ID and count unchanged in the same slot | Row remains; age advances by Pacific calendar date | `stableSinceDate` is preserved; `observedAt` advances |
| Change only the count | Row shows new count and age 0 on that Pacific date | `stableSinceDate` resets; item ID/location remain |
| Replace with another item | Row shows replacement and age 0 | ID/link/icon/count replace prior values; stability resets |
| Empty the slot | Row disappears after success | Slot record is removed |
| Put the item in a different slot | New row/location shows age 0 | New location receives a new stability date |
| Make the tab inaccessible | Tab shows `No access` and prior last-accessible time | Prior slots, their observations, and stability dates are retained |
| Restore access without changing the retained item | Current rows return | `observedAt` and tab `lastAccessibleAt` advance; matching slot stability remains |

- [ ] Every row above was observed, or its deterministic `MVP-E2E-05`
  transition was recorded in automated evidence.

## Scenario 9 — reset, canceled reset, and corrupt-data recovery

- [ ] With populated observations and a saved manual window position, enter
  `/rgms reset` and cancel.
  - Chat: `RGMS: Reset canceled; no data was changed.`
  - UI/timestamp/state: all reports, timestamps, and window position remain.
- [ ] Enter `/rgms reset` again and accept.
  - Chat: `RGMS: Roster and bank observations reset; window position
    preserved.`
  - UI: both reports return to their no-data states.
  - Timestamp/state: roster/bank guilds and timestamps are absent; collections
    are empty; `ui.windowPosition` is preserved.
- [ ] Fully close Retail. Back up the file, then replace only
  `RGMSCharacterDB` with an invalid value such as `RGMSCharacterDB = "corrupt"`.
  Start Retail and decline recovery.
  - Chat: RGMS says saved data is corrupt and later says recovery was canceled,
    RGMS remains disabled, and `/rgms reset` can recover it.
  - UI: both refresh controls are disabled and both views explain recovery.
  - Timestamp/state: the original invalid value is not replaced.
- [ ] Restart with the same corrupt value and accept recovery.
  - Chat: `RGMS: Saved data reset completed; scans and reports are enabled.`
  - UI: controls return according to guild/bank availability.
  - Timestamp/state: schema version 7 empty observations replace the corrupt
    value; a valid recoverable window position is retained if present.
